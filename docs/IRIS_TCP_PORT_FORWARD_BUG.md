# Bug Report: TCP Port-Forward — Guest→Host Data Not Forwarded

**Repository:** https://github.com/techomancer/iris  
**Component:** NAT / TCP port-forward  
**IRIS version:** (built from main, 2026-05-23)  
**Host OS:** Windows 11 Pro (build 26200.8037)  
**Guest OS:** IRIX 5.3 (SGI Indy R4400, pre-installed MAME image)

---

## Summary

TCP port-forwards work in the host→guest direction only. Data sent by the
IRIX guest back to the Windows host is received by the IRIS NAT layer
(`in_flight` counter advances) but is never written to the Windows-side
socket. The guest receives no TCP ACK and eventually retransmits indefinitely.

---

## Configuration

`iris53.toml` excerpt:

```toml
[[port_forward]]
proto      = "tcp"
host_port  = 8753
guest_port = 8753
bind       = "localhost"
```

IRIX guest networking:
- Interface: `ec0` at `192.168.0.2`, netmask `255.255.255.0`
- Gateway: `192.168.0.1` (IRIS NAT)
- Interface confirmed up: `ifconfig ec0` shows `RUNNING`
- Connectivity confirmed: `ping -c 1 192.168.0.1` succeeds

---

## Reproduction Steps

1. Start IRIS with the above `toml`. Guest boots to IRIX 5.3.
2. Configure guest networking (ec0 at 192.168.0.2, route via 192.168.0.1).
3. On IRIX, start a simple TCP server on port 8753 (e.g., inetd spawning any
   service, or a custom program that calls `accept()` then writes a response).
4. From Windows, connect: `telnet localhost 8753`
5. Send any data from Windows → IRIX receives it (host→guest direction works).
6. IRIX writes a response back (guest→host direction).
7. Observe: Windows receives nothing. `telnet` hangs waiting for data.

---

## Monitor Evidence

With `net debug tcp on` and then `net status tcp` in the IRIS monitor
(`telnet localhost 8888`), the NAT table shows:

```
slot  proto  state        local              remote               in_flight  rtx    cli_win
0     TCP    ESTABLISHED  192.168.0.2:8753   192.168.0.1:NNNNN    152B       1/152B  61440
```

Key observations from this output:

| Field | Value | Interpretation |
|---|---|---|
| `state` | `ESTABLISHED` | TCP handshake completed; connection is active |
| `in_flight` | `152B` | IRIS NAT has received 152 bytes from the guest TCP stack |
| `rtx` | `1/152B` | Guest has retransmitted (no ACK received) |
| `cli_win` | `61440` | Windows-side receive window is 60KB — **not** flow-controlled |

The 152 bytes are a real application response — in this case, a valid MCP
JSON-RPC `initialize` response generated by a daemon running on IRIX. The
IRIX syslog confirmed the daemon processed the request and called `write()`
on the TCP socket:

```
mcpserverd[NNN]: ipc: client connected
mcpserverd[NNN]: protocol: initialize from stdio
mcpserverd[NNN]: spawned handler pid NNN
```

---

## Analysis

The data flow breaks after IRIS NAT receives the guest data:

```
IRIX app write()
  → IRIX TCP stack
    → IRIS NAT (in_flight advances to 152)   ← data arrives here
      → Windows TCP socket write()           ← this step does NOT happen
        → Windows telnet client
```

Because IRIS NAT does not send a TCP ACK back to the guest, the guest TCP
stack retransmits. The Windows-side socket window is non-zero (`cli_win=61440`),
ruling out TCP flow control as the cause.

The host→guest direction works correctly: data sent by Windows is received by
the IRIX application.

---

## Impact

- Any TCP service on IRIX 5.3 that replies to incoming connections is
  effectively unreachable from the Windows host.
- inetd-based services (telnet, MCP, etc.) accept connections but cannot
  send responses back.
- The port-forward configuration is correct; the issue is in the IRIS NAT
  forwarding logic.

---

## Additional Notes

- The telnet forward (host 2323 → guest 23) exhibits the same behavior:
  IRIX accepts the telnet connection and sends its greeting/login prompt,
  but Windows telnet receives nothing. This is consistent with the same
  guest→host forwarding failure.
- Tested with `net debug tcp on` — no additional debug output appeared on
  the monitor console when guest data arrived (may be a useful insertion point).
- This was confirmed on IRIS built from the `main` branch as of 2026-05-23.

---

## Workaround

None available from the host side. As a partial workaround, the IRIS serial
console (monitor port 8881, raw TCP) and the IRIS emulator monitor
(`telnet localhost 8888`) are both unaffected and remain functional for
interactive use.
